# TASK-001 API Integration: Sessions (Provisional Mock Contract)

Source: `tasks/TASK-001/requirements.md`, `tasks/TASK-001/architecture.md`. Defines the frontend-facing contract for the `sessionsApi.ts` module architecture.md placed at `src/features/sessions/sessionsApi.ts`.

## Contract Status

This entire document is a **provisional mock schema**, not a confirmed backend contract. The task explicitly excludes a real backend ("Do not implement a backend service"), so there is no backend owner to confirm field names, status values, or error shapes against — the "boundary" being contracted here is a client-only module (`sessionsApi.ts` backed by `mockSessionsStore.ts`), not a real HTTP API. Per the contract-evidence rule, this must stay visibly provisional and **must not** be copied into `specs/api-integration.md` as confirmed integration truth — it describes the mock's working shape for this task, owned by the developer implementing it, not by an external backend team.

If a real backend for training sessions is ever introduced later, this whole document is superseded and needs re-confirmation against that backend's actual contract.

## Classification

- **Confirmed (from requirements.md, not from any backend):** title must be trimmed, 3–80 chars; start date/time must be strictly in the future at submission; the filter control offers exactly `All` plus one selectable status at a time; no backend service exists; duplicate submission must be prevented while a create request is pending.
- **Proposed (this document, needs developer/coder sign-off before implementation, listed in full below):** `Session` / `CreateSessionInput` shapes, `SessionStatus` enum values, `listSessions`/`createSession` signatures, error shape, id generation, default status on create.
- **Assumed:** client-side validation (title/date rules) fully gates calls to `createSession` — the mock does not need to re-validate business rules, only simulate persistence and transport-level failure.
- **Blocked:** none. There is no external party to block on; every open item below is a same-repo decision.

## Provisional Types

```ts
type SessionStatus = 'scheduled' | 'completed' | 'cancelled'

interface Session {
  id: string
  title: string
  status: SessionStatus
  startAt: string // ISO 8601, UTC, e.g. "2026-10-01T14:00:00.000Z"
}

interface CreateSessionInput {
  title: string
  startAt: string // ISO 8601, produced from the form's local date + time fields
}
```

- `id`: generated by `mockSessionsStore` on create (proposed: `crypto.randomUUID()`, available in both browser and Vitest/jsdom/Node runtimes — no new dependency). Never supplied by the caller.
- `title`: stored exactly as validated by `CreateSessionForm` (already trimmed, 3–80 chars) — the mock does not re-trim or re-validate.
- `status`: not supplied by the caller on create; see "Default status on create" below.
- `startAt`: always ISO 8601 in both directions (list output and create input), so the UI does one date-parsing strategy regardless of source.

## Operations

### `listSessions(): Promise<Session[]>`

- **Input:** none.
- **Success:** resolves with the current in-memory session array (seed data plus any created this session), after a simulated delay.
- **Empty case:** resolves with `[]` when there are no sessions (e.g., seed data cleared) — not a rejection. Not explicitly required by any acceptance criterion; flagged under Open Questions below so it's a conscious choice, not an accidental gap.
- **Failure:** rejects with `Error(message)` where `message` is user-presentable (see Error Copy below). Per architecture.md, the failure/success outcome must be deterministically controllable from tests (a test-only seam on `mockSessionsStore`, e.g. `setNextListOutcome('success' | 'error')`), not randomized — required for acceptance criterion 3 (error + retry) to be reliably testable and manually reproducible.

### `createSession(input: CreateSessionInput): Promise<Session>`

- **Input:** `{ title, startAt }`, already validated by `CreateSessionForm` before this is ever called. The mock does not need to defend against invalid title length or a past `startAt` — those never reach this function under correct UI behavior, so no duplicate validation-error path is defined here.
- **Success:** resolves with the full created `Session` (server/mock-assigned `id`, echoed `title`/`startAt`, and an assigned `status`) after a simulated delay, and the mock store appends it so a subsequent `listSessions()` call would include it too.
- **Default status on create (proposed):** `'scheduled'` — a session created with a future `startAt` hasn't happened yet. No other default was requested; flagged as a proposed default, not a confirmed rule.
- **Failure:** rejects with `Error(message)`. Recommend the same kind of deterministic test-only seam as `listSessions` (e.g. `setNextCreateOutcome(...)`) for symmetry and future test coverage, though only one essential test is required by scope and it may not need this path.
- **Idempotency/duplicates:** not required. The task only requires preventing a *second submission of the same in-flight request* (via UI disabling the submit control), not preventing two sessions with identical titles — no uniqueness constraint is proposed.

## Error Shape

Both operations reject with a plain `Error` (architecture.md's choice — no custom error class hierarchy at this scale):

```ts
Error("Could not load sessions. Please try again.")   // listSessions failure
Error("Could not create the session. Please try again.") // createSession failure
```

`useSessions` reads `error.message` directly into `listError` / `createError`. These are proposed copy, not final UX copy — `coder`/`ui-designer` may adjust wording as long as each message stays specific and actionable (per requirements' "useful validation/error message" criteria).

## State / Error Matrix

| State | Trigger | User-visible behavior | Owning region |
|---|---|---|---|
| List loading | mount, or retry after error | loading indicator, no rows | `SessionList` |
| List ready (populated) | `listSessions()` resolves with ≥1 item | rows rendered, filter usable | `SessionList` + `SessionFilter` |
| List ready (empty) | `listSessions()` resolves with `[]` | *(open question — see below)* | `SessionList` |
| List error | `listSessions()` rejects | error message + retry control; rest of UI stays usable | `SessionList` |
| Filter narrowed | user selects a specific status | only matching sessions visible | `SessionList` (derived from `useSessions`) |
| Create idle | form opened, untouched | fields empty/enabled | `CreateSessionForm` |
| Create validation error | submit with invalid title/date | per-field message, no request sent | `CreateSessionForm` |
| Create submitting | valid submit, request pending | submit control disabled/unavailable | `CreateSessionForm` |
| Create success | `createSession()` resolves | new session visible in list (respecting active filter); form resets/closes | `CreateSessionForm` → list |
| Create error | `createSession()` rejects | inline error near submit; entered values preserved; list untouched | `CreateSessionForm` |

## Not Applicable (explicitly, per client-behavior rule)

- **Permission/auth errors:** no authentication or authorization is in scope for this task; there is exactly one implicit trainer user.
- **Malformed external data:** the mock is entirely self-controlled by this codebase, so there is no untrusted external payload shape to defend against.
- **Caching, cache invalidation, staleness, deduplication:** no server-state caching layer (architecture.md rejected adding one); sessions are fetched once on mount and updated locally on create.
- **Cancellation/timeout:** the mock's simulated latency is bounded and synthetic, so there's no real network hang to guard against. An `AbortController` on unmount is a possible defensive nicety but is not required by any acceptance criterion.

## Test Strategy

- The one required essential test (per requirements.md, AC10) exercises either the filter flow or the create-success flow behaviorally through `SessionsWorkspace`, using Testing Library + Vitest — it does not need to touch `sessionsApi` internals directly, only observe rendered outcomes.
- `validation.ts` (title bounds, future-date check) is pure and cheaply unit-testable in isolation if the developer chooses to add coverage beyond the one essential test — optional, since "full test coverage" is an explicit non-goal.
- If a test targets the list-error/retry path (AC3), it needs the deterministic outcome seam described under `listSessions` above; without it, that path can only be exercised manually.

## Open Questions / Flags for `writing-plans` and `coder`

1. **Empty-list state:** not named by any acceptance criterion or by `TASK.md`. Recommend a small "No sessions yet" message in `SessionList` for a sane UX, but this is optional scope, not a requirement — call it out explicitly rather than silently add or silently omit it.
2. **`SessionStatus` enum values** (`scheduled | completed | cancelled`, carried over from architecture.md): proposed, not sourced from any backend. Confirm this set is what the create form's implicit status assignment and the filter control's options should use before locking `types.ts`.
3. **Default status on create** (proposed `'scheduled'`): confirm this is the intended behavior; no alternative was requested.
4. **id generation** (`crypto.randomUUID()`): fine for a mock; noted only so it isn't mistaken for backend-assigned id logic if a real API ever replaces this module.

None of these block starting implementation — each has a stated default with rationale. Only item 1 could change the plan's file/step list if the developer wants an explicit empty state included.

None. There is no backend to confirm against for this task — it is explicitly out of scope. This contract is provisional to `TASK-001` only.
